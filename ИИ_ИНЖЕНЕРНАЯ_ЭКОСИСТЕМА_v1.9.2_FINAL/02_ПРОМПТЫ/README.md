# Каталог ролевых промптов

## Назначение документа

Этот документ объясняет, какую роль выполнять с помощью каждого промпта, в каких случаях его подключать, какие материалы передавать и какой результат ожидать. Он предназначен одновременно владельцу системы и ИИ, который разбирается в доступном комплекте.

**Актуальные версии и канонические пути определяются только корневым `README.md`, разделом «Единственный реестр состава и версий».** Этот каталог описывает назначение ролей и правила их выбора. Он не создаёт отдельного источника версий и не отменяет содержимое самих промптов.

Промпты являются самостоятельными инструкциями. Обычно в чат подключается один основной промпт — тот, чья функция соответствует текущей задаче. Наличие остальных файлов в архиве не означает, что все роли одновременно запущены, имеют общий контекст или автоматически обмениваются сообщениями.

---

## Общий стиль текстовых результатов

Документы экосистемы оформляются по корневому [`00_СТАНДАРТ_ДОКУМЕНТАЦИИ.md`](../00_СТАНДАРТ_ДОКУМЕНТАЦИИ.md). Он задаёт общий профессиональный голос, правила терминологии и разные структуры для разных типов материалов. Это не универсальный шаблон: формат результата определяется задачей и контрактом конкретной роли.

Если стандарт не передан в отдельный чат, ролевой промпт содержит краткое правило естественного и точного изложения. Наличие или отсутствие файла стандарта не меняет обязательные форматы, полномочия и ограничения роли.

## 1. Как выбрать нужную роль

Начинай выбор с требуемого результата, а не с названия доступного промпта.

- Нужно определить, **что делать, в каком порядке и кого привлечь** — используй Router.
- Нужно **изучить проект, спроектировать решение, написать или изменить код, выполнить проверки и подготовить результат** — используй Worker.
- Нужно **независимо проверить готовый результат и найти дефекты или риски** — используй Critic.
- Нужно **извлечь повторно используемые знания из реальной работы** — используй Extractor.
- Нужно **проверить подготовленные записи перед размещением в базе знаний** — используй Sorter.
- Нужно **провести аудит уже существующей базы знаний** — используй Consolidator.

Не запускай все роли «на всякий случай». Подключай следующую роль только тогда, когда её результат нужен для принятия решения или безопасного продолжения.

### 1.1. Быстрые ориентиры

**Router отвечает на вопрос:** «Какой путь решения задачи будет наиболее подходящим?»

**Worker отвечает на вопрос:** «Как исследовать, спроектировать, реализовать и проверить решение?»

**Critic отвечает на вопрос:** «Соответствует ли результат исходным требованиям и какие подтверждённые проблемы остались?»

**Extractor отвечает на вопрос:** «Какой проверяемый опыт стоит сохранить, чему он учит и где его можно применить?»

**Sorter отвечает на вопрос:** «Соответствует ли подготовленная запись правилам базы знаний и куда её предлагается поместить?»

**Consolidator отвечает на вопрос:** «Насколько согласована и актуальна переданная база знаний, где есть дубликаты, конфликты и пробелы?»

## 2. Router — системный координатор

**Активный файл:** [`PROMPT_ROUTER_UNIVERSAL_v2.1.5.md`](PROMPT_ROUTER_UNIVERSAL_v2.1.5.md)

### Для чего предназначен

Router — центральная роль координации. Он разбирает запрос пользователя, устанавливает цель и ограничения, ориентируется в фактически доступной архитектуре, выбирает подходящий маршрут, определяет нужные роли и материалы, формирует поручения, устанавливает критерии приёмки и точки согласования. Router также помогает выявлять системные пробелы и готовить контролируемые предложения по развитию экосистемы.

Router нужен не для того, чтобы лично выполнять всю работу, а чтобы выбрать правильный способ её выполнения и сохранить целостность процесса.

### Когда подключать

Подключай Router, когда:

- задача многоэтапная, затрагивает несколько инженерных областей или ролей;
- пока неясно, нужен ли Worker, Critic или контур базы знаний;
- требуется разделить большую цель на задачи и контрольные точки;
- нужно подготовить точное поручение Worker или пакет передачи другой роли;
- нужно оценить влияние предполагаемого изменения на архитектуру экосистемы;
- требуется перенести управление проектом или системой в другой чат;
- нужно сопоставить доступные компоненты, обнаружить конфликт версий или определить, каких материалов не хватает.

Для небольшого вопроса, на который можно ответить непосредственно по предоставленным материалам, отдельный запуск Router не обязателен.

### Что передавать Router

Для выбора маршрута обычно достаточно описания цели и ожидаемого результата. Для системных выводов и работы с архитектурой дополнительно передавай:

- корневой `README.md` с реестром активного комплекта;
- `START_HERE.md`, если Router впервые подключается к системе;
- README соответствующих подсистем;
- текущий проектный контекст и ограничения, если задача относится к проекту;
- контракт ручной передачи, если готовится межролевой handoff;
- полные документы или фрагменты, по которым требуется вынести архитектурное решение.

Не нужно автоматически загружать всю Методику, всю базу знаний и все промпты. Передавай их по мере необходимости.

### Что Router возвращает

В зависимости от задачи результатом будет:

- краткий обоснованный маршрут;
- перечень нужных ролей с объяснением их участия;
- план этапов, зависимостей и контрольных точек;
- точное поручение Worker или другого исполнителя;
- пакет передачи контекста;
- описание системной проблемы и предложение по её исправлению;
- список неизвестных и необходимых согласований.

### Чего Router не делает

Router не пишет реализационный код, не запускает тесты, скрипты и валидаторы, не исследует технические детали репозитория вместо Worker, не проводит независимый аудит вместо Critic и не вносит самостоятельные изменения в глобальные промпты, Методику, контракты или базу знаний. Он не получает автоматический доступ к другим чатам.

### Самостоятельный запуск

Router можно подключить одним промптом. Без корневого README его карта ролей и сведения о версиях являются предварительными. Он может помочь с маршрутизацией обычной задачи, но обязан обозначать непроверенные сведения и не выдавать отсутствующие файлы, проекты или знания за доступные.

## 3. Worker / Programmer — инженерный исполнитель

**Активный файл:** [`PROMPT_PROGRAMMER_UNIVERSAL_v1.3.3.md`](PROMPT_PROGRAMMER_UNIVERSAL_v1.3.3.md)

### Для чего предназначен

Worker — основная исполнительная роль для инженерной работы. Он исследует существующий проект и технические варианты, анализирует требования, проектирует архитектуру, реализует функции, исправляет дефекты, работает с кодом и интеграциями, проводит доступные проверки, готовит документацию и передаёт проверяемый результат.

Worker способен работать как непосредственно с пользователем, так и по поручению Router. Отсутствие Router не блокирует прямую инженерную работу.

### Когда подключать

Подключай Worker, когда требуется:

- создать новый программный продукт или компонент;
- исследовать существующий код, архитектуру, API или зависимости;
- исправить дефект или выполнить рефакторинг;
- интегрировать библиотеку, сервис или готовый проект;
- провести технические проверки и собрать evidence;
- подготовить изменения в документации, конфигурации или системных файлах в явно согласованном scope;
- продолжить работу по передаточному пакету из другого чата.

### Что передавать Worker

Минимальный пакет должен содержать понятную цель и ожидаемый результат. Для реальной разработки также нужны доступные исходники или репозиторий, контекст проекта, требования, критерии приёмки, ограничения, известные решения и разрешённый scope.

При запуске через Router передавай его поручение и приложенные материалы. При прямом запуске пользователь может дать задачу непосредственно — Worker сам изучит доступный контекст и задаст только необходимые вопросы.

Методика, Skills и общая база знаний являются дополнительными материалами. Worker не должен останавливаться только потому, что они не приложены, и не должен заявлять, что применил разделы, которые фактически не читал.

### Режимы работы

Промпт Worker разделяет несколько независимых осей настройки:

- **Автономность A / B / AUTO:** от строгого исполнения заданного направления до самостоятельной инженерной работы в рамках полномочий. AUTO используется по умолчанию, если пользователь не указал иное.
- **Инженерный режим Explore / Produce / Hotfix:** исследование и снижение неопределённости; плановая разработка; либо ограниченное срочное исправление.
- **Глубина объяснения Guided / Standard / Expert:** от подробного объяснения шагов до профессионального технического изложения.
- **Настройка сотрудничества:** исходные предпочтения и способ взаимодействия уточняются отдельно и не должны смешиваться с перечисленными режимами.

Не нужно включать все режимы вручную при каждой задаче. Worker выбирает подходящий профиль на основании запроса и явно заданных предпочтений пользователя.

### Что Worker возвращает

В нормальном завершении Worker сообщает, что именно изучено и изменено, какие файлы затронуты, какие решения приняты, какие тесты действительно запускались и с каким результатом, что осталось непроверенным, какие риски сохраняются и как продолжить работу.

При необходимости он создаёт файлы или архив, готовит пакет Critic, передаточное резюме или кандидаты уроков для Extractor.

### Чего Worker не делает

Worker не должен выдавать собственную проверку за независимый аудит Critic. Он не должен незаметно расширять scope, выполнять необратимые или высокорисковые действия без разрешения, раскрывать секреты или утверждать неподтверждённые результаты. Глобальные изменения системы требуют предусмотренного согласования владельца.

### Самостоятельный запуск

Worker рассчитан на самостоятельный запуск без полного ZIP. Для конкретной задачи ему необходимы сама постановка и доступные материалы проекта. Если отсутствуют репозиторий, код, конфигурация или инструменты, Worker обозначает границы проверки и не имитирует недоступные операции.

## 4. Critic — независимый проверяющий

**Активный файл:** [`PROMPT_CRITIC_UNIVERSAL_v1.1.2.md`](PROMPT_CRITIC_UNIVERSAL_v1.1.2.md)

### Для чего предназначен

Critic независимо оценивает проект и результат работы относительно исходной цели, требований пользователя, scope, архитектуры, критериев приёмки и фактических артефактов. Он ищет дефекты, несоответствия, уязвимости, ошибки интеграции, пробелы тестирования, эксплуатационные риски и другие проблемы, которые автор реализации мог не заметить.

Его независимость — отдельный механизм качества. Critic не является продолжением самооценки Worker.

### Когда подключать

Подключай Critic, когда:

- изменение затрагивает безопасность, данные, авторизацию, платежи, инфраструктуру или другие чувствительные области;
- проект или интеграция достаточно сложны, чтобы оправдать независимый взгляд;
- требуется проверка перед важным релизом или передачей результата;
- пользователь прямо запросил независимый аудит;
- Worker завершил значимый этап и требуется проверка относительно исходных требований;
- после исправлений нужно проверить закрытие findings и отсутствие регрессий.

Не нужно запускать Critic после каждой незначительной правки, если независимая проверка не изменит качество или безопасность решения.

### Два основных режима проверки

**`BLIND_REVIEW` — первое независимое рассмотрение.** Critic получает исходные требования, scope, критерии, фактические артефакты и разрешённые границы проверки. Ему не передают выводы Worker и перечень ожидаемых проблем как направление поиска. Это защищает независимость первичного review.

**`REVIEW_CONTINUATION` — продолжение уже начатой проверки.** Critic получает новую ревизию или diff, предыдущие findings с неизменными ID, ответы Worker, доказательства исправлений и результаты повторных проверок. Он проверяет закрытие прежних замечаний и возможные побочные эффекты.

### Что передавать Critic

Для содержательного review нужны исходная цель и требования, согласованный scope, точная ревизия кода или артефактов, архитектурный контекст, критерии приёмки, фактические результаты тестов и известные ограничения. Если часть данных не предоставлена, Critic отмечает ограничения покрытия.

### Что Critic возвращает

Результат — отчёт независимой проверки: findings со стабильными ID, серьёзностью, доказательствами, условиями воспроизведения и рекомендациями; матрица покрытия; непроверенные области; ограничения; оценка остаточного риска и приоритет дальнейших действий.

### Чего Critic не делает

По умолчанию Critic работает в `READ-ONLY REVIEW`: не меняет исходники, не перемещает файлы, не закрывает finding за Worker и не объявляет исправление выполненным без подтверждения. Активные проверки, fuzzing, нагрузочные или атакующие действия допустимы только в явно разрешённой среде и пределах scope.

### Самостоятельный запуск

Critic может работать без полного ZIP, если предоставлены сам промпт, исходные требования и фактически проверяемые материалы. Получение досье без кода означает понимание контекста, но не проведённый аудит.

## 5. Extractor — извлечение и курирование инженерных знаний

**Активный файл:** [`ПРОМПТ_ЭКСТРАКТОРА_v1.4.3.md`](ПРОМПТ_ЭКСТРАКТОРА_v1.4.3.md)

### Для чего предназначен

Extractor анализирует реальные рабочие материалы и выделяет знания, которые могут пригодиться повторно. Он превращает подтверждённый опыт в кандидаты записей базы знаний, сохраняя источник, доказательства, уровень уверенности, область применимости и ограничения.

Основные типы записей:

- **SKILL** — воспроизводимая процедура или технический навык. Создание SKILL допускается только после предусмотренного `Outcome Gate`.
- **EXPERIENCE** — запись отдельного практического эпизода, включая частичный результат, неудачу, причину отказа и уроки.
- **INSIGHT** — ограниченное обобщение, опирающееся на явно перечисленные свидетельства.

Extractor также фиксирует полезную Negative Memory: отвергнутый вариант, контекст, причину отказа, доказательства и условия, при которых решение можно пересмотреть.

### Когда подключать

Используй Extractor после существенного инженерного эпизода, например:

- подтверждённого дефекта, инцидента или near miss;
- повторяющейся ошибки или повторного переделывания работы;
- успешно решённой сложной задачи с воспроизводимым методом;
- независимого finding Critic и последующего подтверждённого исправления;
- важного архитектурного решения;
- отказа от альтернативы, если причина отказа полезна в будущем;
- завершения большого этапа или проекта;
- обнаружения повторяющегося пробела в процессах или документации.

Не запускай полный процесс извлечения после каждого мелкого сообщения. Если переносимого знания нет, допустимый результат — `NO_KNOWLEDGE_EXTRACTED`.

### Что передавать Extractor

Передавай первичные материалы: диалог или его точные релевантные части, отчёты, diff, commit/revision, тестовые логи, findings Critic, подтверждение пользователя и сведения о проекте. Обозначь границы анализа и ограничения приватности. Пересказ одной роли не должен подменять доступный первичный источник.

### Что Extractor возвращает

Extractor готовит один или несколько кандидатов записей с YAML frontmatter и телом по актуальным шаблонам. Каждый кандидат должен иметь происхождение, claims, evidence, статус и область применимости. Файлы предназначаются для `04_INBOX/НОВЫЕ/`, но роль не выполняет физическое размещение.

### Чего Extractor не делает

Extractor не создаёт `PROJECT_CONTEXT`, не переписывает существующую базу знаний, не обновляет индекс, не перемещает файлы и не утверждает глобальные правила. Единичное наблюдение не превращается автоматически в универсальную процедуру. Без полного индекса нельзя заявлять о глобальной дедупликации.

### Самостоятельный запуск

Extractor может анализировать переданные источники без полного ZIP. Отсутствие индекса ограничивает глобальную сверку, но не блокирует локальное извлечение. Отсутствующие шаблоны и материалы не должны объявляться прочитанными.

## 6. Sorter — проверка подготовленных записей

**Активный файл:** [`ПРОМПТ_СОРТИРОВЩИКА_v1.4.3.md`](ПРОМПТ_СОРТИРОВЩИКА_v1.4.3.md)

### Для чего предназначен

Sorter выполняет техническую проверку записей, подготовленных для базы знаний. Он проверяет YAML frontmatter, соответствие schema 1.2, обязательные поля, ID, названия, тип записи, согласованность статусов, целевой каталог, потенциальные дубликаты и основания для приоритета.

Его задача — не извлекать знания и не решать, является ли новая идея истинной сама по себе, а проверить, правильно ли оформлена и подготовлена конкретная запись, и какие действия можно предложить владельцу.

### Когда подключать

Подключай Sorter, когда Extractor или человек подготовил одну или несколько новых записей и их нужно проверить перед ручным размещением. Он также подходит для повторной проверки исправленной записи или ограниченного набора материалов.

Не используй Sorter вместо Extractor для анализа переписки и не запускай его для аудита всей базы знаний — это задача Consolidator.

### Два уровня проверки

**`LOCAL_VALIDATION`** применяется, когда переданы только отдельные записи и встроенные правила schema 1.2. Sorter может проверить локальную структуру, но глобальные конфликты, дубликаты и полноту приоритета остаются `UNKNOWN` или `NOT_CHECKED`.

**`PACKAGE_AWARE_VALIDATION`** допустим, когда дополнительно фактически предоставлены актуальные индекс, реестр проектов и необходимые записи. Только в пределах реально прочитанного набора можно делать соответствующие перекрёстные выводы.

### Что передавать Sorter

Передавай полные файлы записей, а не только их краткое описание. По возможности приложи актуальные шаблоны, индекс знаний, реестр проектов и необходимые связанные записи. Явно укажи требуемый scope проверки, если он не очевиден.

### Что Sorter возвращает

Sorter выдаёт отчёт `DRY RUN`: результаты структурной проверки, найденные ошибки и предупреждения, дубликаты-кандидаты, предлагаемые пути и приоритеты, основания рекомендаций и последовательность ручных действий после одобрения.

### Чего Sorter не делает

Sorter строго ограничен `DRY_RUN_ONLY`. Он не исправляет YAML или содержимое файлов, не перемещает и не переименовывает записи, не создаёт записи в базе, не обновляет индекс и не выполняет Git-операции. Даже правильное предложение Sorter остаётся предложением до решения владельца и ручного применения.

### Самостоятельный запуск

Sorter может проверить отдельную запись без полного ZIP, используя встроенные правила schema 1.2. При этом он обязан явно ограничить выводы локально проверенным материалом.

## 7. Consolidator — аудит базы знаний

**Активный файл:** [`ПРОМПТ_КОНСОЛИДАТОРА_v1.4.3.md`](ПРОМПТ_КОНСОЛИДАТОРА_v1.4.3.md)

### Для чего предназначен

Consolidator проводит периодический или заказанный аудит уже накопленной базы знаний. Он анализирует структуру, индекс, записи, происхождение, качество доказательств, дубликаты, противоречия, актуальность, приоритеты HOT/WARM/COLD и показатели зрелости. Результатом становятся выводы и предложения по дальнейшему улучшению.

Это не этап первичной сортировки одной новой записи. Его задача — оценить состояние базы как системы в пределах реально предоставленных данных.

### Когда подключать

Используй Consolidator:

- при плановом аудите базы знаний;
- после накопления значительного массива новых или изменённых записей;
- когда появились подозрения на дубликаты, конфликты или устаревшие знания;
- когда требуется проверить согласованность индекса, каталогов и статусов;
- когда нужно оценить зрелость записей и подготовить предложения по Методике.

Не запускай его после каждой небольшой записи. Для локальной проверки одной новой записи предназначен Sorter.

### Два уровня аудита

**`SCOPED_AUDIT`** — проверка только фактически предоставленной выборки или подсистемы. Она не доказывает полноту всей базы, отсутствие глобальных дублей или полное соответствие индекса.

**`PACKAGE_AWARE_AUDIT`** — проверка при наличии актуального индекса, полного набора записей в заявленном scope, реестра проектов и необходимых журналов. Полнота должна быть доказана инвентаризацией, а не предположена по названию ZIP.

### Что передавать Consolidator

Передавай индекс и записи в нужном объёме, проектный реестр, относящиеся к аудиту PROJECT_CONTEXT, предыдущие отчёты, журналы изменений и подтверждённые USED-сигналы, если они есть. Обозначь цель аудита и границы выборки.

### Что Consolidator возвращает

Результат включает границы и полноту аудита, executive summary, findings, проблемы схемы и provenance, анализ Outcome Gate, оценку RUBRIC, предложения по HOT/WARM/COLD, дубликаты и конфликты, предложения по index reconciliation, улучшения Методики и очередь решений владельца.

### Чего Consolidator не делает

Consolidator работает в `READ_ONLY` режиме. Он не редактирует, не перемещает и не удаляет записи, не обновляет индекс, не меняет статусы и приоритеты автоматически, не делает Git-коммиты и не переписывает глобальные инструкции. Он не объявляет полный аудит, если просмотрен только фрагмент данных.

### Самостоятельный запуск

Consolidator может выполнять локальный аудит переданного набора без полного ZIP. Объём вывода должен соответствовать фактическому scope: частичная выборка — это scoped audit, а не аудит всей базы.

## 8. Как роли взаимодействуют

### 8.1. Обычная инженерная задача

`Пользователь → Router → Worker → результат → Router / пользователь`

Critic подключается, когда независимая проверка оправдана масштабом, риском или требованиями приёмки. Extractor подключается после существенной работы, если есть переносимый опыт.

### 8.2. Независимый цикл проверки

`Worker → Critic (BLIND_REVIEW) → Worker (исправления) → Critic (REVIEW_CONTINUATION)`

Для первого `BLIND_REVIEW` Critic получает исходные требования и артефакты, но не получает выводы Worker, способные направить или исказить поиск. При продолжении проверки сохраняются IDs findings, чтобы не потерять историю и не создавать повторные замечания под новыми номерами.

Critic не исправляет код. Worker не может закрыть finding только собственным заявлением; требуется фактическое исправление и соответствующая проверка.

### 8.3. Накопление инженерных знаний

`Реальные материалы → Extractor → 04_INBOX/НОВЫЕ → Sorter (DRY RUN) → решение владельца → ручное размещение в 03_БАЗА_ЗНАНИЙ → обновление индекса → Consolidator по необходимости`

Extractor готовит содержательные записи. Sorter проверяет их оформление и предлагает размещение. Пользователь принимает решение и выполняет разрешённые операции. Consolidator позднее проверяет согласованность базы. Ни одна из этих ролей не получает автоматического права изменять глобальную базу.

### 8.4. Развитие самой экосистемы

`Проблема или предложение → Router определяет затронутые активы → при необходимости Extractor собирает доказательства → Worker готовит изменение → Critic независимо проверяет → владелец утверждает → изменение применяется и проверяется`

Sorter и Consolidator подключаются только тогда, когда изменение затрагивает структуру или записи базы знаний. Предложение, утверждение, реализация и проверка — разные состояния.

### 8.5. Не смешивай контексты

Каждая роль обычно запускается в отдельном чате или отдельном изолированном контексте. Загрузка промпта Worker не запускает Critic. Наличие Router не означает, что он видит другие чаты. Между ними используется ручная передача материалов по контракту.

## 9. Самостоятельный запуск и подключение полного комплекта

### 9.1. Если запускается один промпт

1. Передай полный файл промпта нужной роли.
2. Передай задачу и минимально необходимые входные материалы.
3. Укажи конкретные ограничения, разрешения и ожидаемый формат результата, если они важны и ещё не содержатся в контексте.
4. Попроси роль подтвердить, какие материалы она действительно получила и прочитала.
5. Не требуй загрузить весь ZIP, если локальная задача может быть выполнена без него.

Самостоятельность промпта означает, что у роли есть базовая процедура и полномочия для выполнения локальной функции. Она не означает, что роль знает состав всей экосистемы, содержание непереданной Методики, состояние базы знаний или детали конкретного проекта.

### 9.2. Если запускается роль в составе экосистемы

1. Передай корневой `README.md` и `START_HERE.md`.
2. Передай README папки `02_ПРОМПТЫ`, чтобы определить назначение и выбрать активную роль.
3. Передай полный промпт только запускаемой роли.
4. Добавь контракт ручной передачи, если планируется handoff.
5. Подключай карту Методики, а затем релевантные полные разделы, если они нужны.
6. Передавай шаблоны, индекс, реестр проектов и записи базы знаний только при наличии задачи, которая от них зависит.

### 9.3. Правило постепенного раскрытия

Не загружай все документы одновременно. Начинай с источника состава, локального README и промпта роли. Дополнительные документы раскрывай по конкретной потребности. Если роль ссылается на недоступный материал, она должна обозначить его как `NOT_PROVIDED` и не выдавать его за прочитанный.

## 10. Передача между ролями и чатами

Общий контракт ручной передачи находится в [`../07_ПРОТОКОЛЫ/КОНТРАКТЫ_РУЧНОЙ_ПЕРЕДАЧИ.md`](../07_ПРОТОКОЛЫ/КОНТРАКТЫ_РУЧНОЙ_ПЕРЕДАЧИ.md).

Контракт задаёт минимальный транспортный конверт, а состав содержимого определяется ролью и типом задачи. Не используй одинаковый пакет для всех ролей. Router, Worker, Critic, Extractor, Sorter и Consolidator имеют разные потребности к входным данным и формату продолжения.

Для крупных передач можно использовать архив с исходными файлами. Если передача текстовая, материалы делятся на пронумерованные части с единым `transfer_id`; получатель подтверждает фактическое получение, прочтение и комплектность. Нельзя утверждать, что другой чат получил пакет, пока это не подтвердил сам получатель.

## 11. Статусы и ограничения проверки

Все шесть промптов в текущем комплекте имеют статус кандидатных редакций. Статический аудит текста и ссылок не доказывает одинаковое поведение разных моделей. Поведенческая совместимость Router → Worker, реальные циклы Worker ↔ Critic, standalone-запуски остальных ролей и multipart-передачи требуют отдельных испытаний в целевых чатах.

Если роль не получила необходимые входные материалы, соответствующая часть результата должна быть ограничена. Примеры:

- Router без корневого README может предложить только предварительную карту версий.
- Worker без исходников проекта не может подтвердить детали реализации.
- Critic без кода не может заявить, что выполнил code review.
- Extractor без индекса не может подтвердить отсутствие глобальных дубликатов.
- Sorter без индекса и реестра не может подтвердить глобальные конфликты и project-based HOT.
- Consolidator без полного набора записей не может называть scoped audit полным аудитом базы.

Наличие отчёта, промпта, шаблона или тест-плана не является доказательством фактически проведённой проверки.

## 12. Частые ошибки подключения

- **Загружают все шесть промптов в один чат.** Это смешивает роли и не создаёт независимых исполнителей. Подключай одну основную роль и открывай другие отдельно.
- **Ожидают, что Router сам реализует код.** Router маршрутизирует и координирует; реализация относится к Worker.
- **Передают Critic выводы Worker при первом слепом review.** Это снижает независимость. Для `BLIND_REVIEW` передавай первичные требования и артефакты.
- **Просят Extractor сохранять всё подряд.** Он должен извлекать только проверяемое и полезное; `NO_KNOWLEDGE_EXTRACTED` — допустимый результат.
- **Считают DRY RUN Sorter реальным перемещением.** Sorter только предлагает действия.
- **Считают отчёт Consolidator изменением базы.** Consolidator только анализирует и предлагает.
- **Считают, что Методика прочитана по одному факту её наличия в ZIP.** Каждая роль должна открыть релевантный полный раздел перед заявлением о его применении.
- **Путают активный файл с историческим или отдельно загруженным кандидатом.** Сверяй путь и версию по корневому README.
- **Полагаются на автоматическую передачу между чатами.** Передача выполняется вручную; получатель подтверждает комплектность.

## 13. Словарь основных команд и режимов

Названия команд и режимов описаны в полных промптах. Ниже приведены наиболее узнаваемые термины, чтобы пользователь понимал их смысл; этот список не заменяет встроенные инструкции соответствующей роли.

- `AUTO` / `MANUAL` — режимы координации Router.
- `A` / `B` / `AUTO` — варианты автономности Worker.
- `Explore` / `Produce` / `Hotfix` — инженерный режим Worker.
- `Guided` / `Standard` / `Expert` — глубина технического объяснения Worker.
- `BLIND_REVIEW` — первичная независимая проверка Critic.
- `REVIEW_CONTINUATION` — продолжение review с сохранением ID предыдущих findings.
- `EXTRACT KNOWLEDGE` — пакетное извлечение знаний Extractor.
- `EXPERIENCE REVIEW` — разбор отдельного опыта или случая.
- `SESSION HANDOFF` — подготовка передачи состояния работы.
- `LOCAL_VALIDATION` — локальная проверка записей Sorter.
- `PACKAGE_AWARE_VALIDATION` — проверка записей с доступными пакетными индексами и реестрами.
- `SCOPED_AUDIT` — ограниченный аудит предоставленного набора Consolidator.
- `PACKAGE_AWARE_AUDIT` — аудит при наличии необходимых полных источников.

Если пользователь формулирует запрос естественным языком, не требуй точного написания команды, если промпт роли не устанавливает специальное условие.

Тело встроенного Critic должно оставаться синхронным с отдельным промптом. Встроенная копия не означает, что Critic запускается автоматически вместе с Worker.

## 15. Принцип применения

Выбирай роль по требуемому результату, подключай минимально необходимый набор компонентов и передавай каждой роли только те материалы, которые нужны для её функции. Соблюдай границы полномочий, разделяй факты и предположения и не выдавай подготовленное предложение за выполненное действие.
