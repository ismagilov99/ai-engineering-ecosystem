# Шаблоны базы знаний и проектной памяти

Шаблоны задают обязательную форму YAML frontmatter и рекомендуемую структуру текста. Они не являются фактическими записями и не подтверждают правдивость заполненных полей.

## Редакции шаблонов записей

Номер редакции ниже относится к самому шаблону, а не к YAML-схеме или версии всего комплекта:

- `SKILL_TEMPLATE.md` — `v1.3.1`;
- `EXPERIENCE_TEMPLATE.md` — `v1.3.2`;
- `INSIGHT_TEMPLATE.md` — `v1.3.2`;
- `PROJECT_CONTEXT_TEMPLATE.md` — `v1.3.1`.

`SESSION_SUMMARY_TEMPLATE.md` и `CRITIC_INITIALIZATION_DOSSIER_TEMPLATE.md` — операционные формы без YAML-записи глобальной БЗ; они не получают `schema_version` и не проходят валидацию через схему записей 1.2.

## Шаблоны глобальных знаний

- `SKILL_TEMPLATE.md` — воспроизводимая процедура. Применяется только после прохождения Outcome Gate. В теле описываются назначение, предварительные условия, процедура, проверка результата, ограничения, безопасность и evidence.
- `EXPERIENCE_TEMPLATE.md` — отдельный практический эпизод. Фиксирует контекст, цель, действия, результат, успешные и неудачные варианты, Negative Memory, уроки и остаточные риски.
- `INSIGHT_TEMPLATE.md` — ограниченное обобщение. Содержит наблюдение, обобщение, основания, применимость, контрпримеры, отвергнутые варианты и план проверки.

## Шаблоны проектной и операционной памяти

- `PROJECT_CONTEXT_TEMPLATE.md` — операционный контекст одного проекта. Используется в `05_ПРОЕКТЫ/<project_id>/PROJECT_CONTEXT.md`; не включается в глобальный индекс БЗ и создаётся пользователем.
- `SESSION_SUMMARY_TEMPLATE.md` — резюме состояния сессии или этапа для продолжения работы. Это handoff-документ, а не запись глобальной БЗ.
- `CRITIC_INITIALIZATION_DOSSIER_TEMPLATE.md` — стартовое досье для независимого Critic. Его передают вместе с полным промптом Critic и релевантными исходными материалами; оно не является записью БЗ.

## Порядок использования

1. Сначала выбери правильный тип: Skill для воспроизводимой процедуры, Experience для отдельного случая, Insight для ограниченного обобщения, Project Context для состояния проекта.
2. Скопируй соответствующий шаблон, не редактируя оригинал.
3. Замени демонстрационные значения реальными данными. Удали инструкции-шаблонные подсказки из итогового тела там, где они больше не нужны.
4. Не придумывай ID, даты, доказательства, тестовые результаты, пользовательские подтверждения, независимые группы и причины отказов.
5. Если факт неизвестен, используй `null`, `UNKNOWN` или соответствующее пояснение по правилам схемы.
6. Проверь YAML frontmatter по [`СХЕМА_YAML_v1.2.json`](../СХЕМА_YAML_v1.2.json). Эта проверка подтверждает структуру YAML, но не доказывает claims, прохождение Outcome Gate или отсутствие секретов.
7. Сохрани готовую запись в `04_INBOX/НОВЫЕ/` для DRY RUN Sorter. Не помещай её сразу в активную категорию.
8. После явного одобрения пользователя вручную обнови статусы, перемести файл, перепроверь YAML и путь и только затем обнови индекс.

## Единые требования

- Версия YAML — строго `1.2`; не меняй её при заполнении.
- Каждый `main_claim` и элемент `additional_claims` содержит `claim_id`, `text`, `kind`, `source.type`, `source.reference`, `confidence` и `independence_group`.
- `additional_claims` всегда массив, в том числе пустой `[]`.
- Не создавай новые `record_type` и поля для Negative Memory, ADR или других смысловых категорий.
- Не включай секреты, приватные ключи, токены, лишние персональные данные, закрытые URL и частный исходный код.
- PROJECT_CONTEXT не копируй в глобальную БЗ; он имеет отдельный шаблон и реестр.
