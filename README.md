О проекте

ИИ-инженерная экосистема — это структурированная система взаимодействия с искусственным интеллектом, построенная на разделении инженерных задач между специализированными ролями, единых методологических принципах, контролируемой передаче контекста и последовательном накоплении знаний.

Вместо попытки поручить все функции одному универсальному ИИ-агенту система разделяет работу на отдельные направления: координацию, инженерную реализацию, независимую проверку, извлечение опыта, управление знаниями и аудит накопленной базы.

Каждая роль имеет собственную область ответственности, ограничения полномочий, входные требования и ожидаемые результаты.

Общая Методика задаёт инженерную основу работы, а файловая структура обеспечивает сохранение проектного контекста, технических решений и накопленного опыта.

Главная идея проекта — не просто использовать ИИ для выполнения отдельных задач, а создать воспроизводимую и управляемую среду инженерного сотрудничества человека и искусственного интеллекта.

Ключевые принципы

- Разделение ответственности. Каждая роль выполняет определённую функцию и не подменяет полномочия остальных.
- Предотвращение дефектов. Сначала необходимо снижать вероятность ошибок внутри контролируемой реализации: через архитектуру, контракты, типизацию, валидацию, инварианты и тестирование. Затем проектировать устойчивость к внешним отказам.
- Проверяемость результатов. Выводы, решения и заявления о выполненной работе должны опираться на фактические материалы и подтверждения.
- Независимый контроль. Проверка результата отделена от его реализации.
- Управление знаниями. Практический опыт, технические решения, ошибки и полезные наблюдения могут извлекаться, проверяться и систематизироваться.
- Контроль человека. Изменения глобальных правил, методики, промптов и структуры системы не происходят автоматически.
- Минимально достаточный контекст. Ролям передаются необходимые материалы, а не весь массив информации без разбора.
- Прозрачность ограничений. Отсутствующие данные, неподтверждённые предположения и незавершённые проверки обозначаются явно.

Архитектура: шесть специализированных ролей

Экосистема включает шесть функционально разделённых ИИ-ролей.

1. Router — координатор и архитектор

Анализирует запрос, определяет необходимый маршрут работы, разбивает сложные задачи на этапы, выбирает роли, формирует поручения и критерии приёмки.

Основная задача: обеспечить правильную организацию инженерного процесса.

2. Worker / Programmer — инженерный исполнитель

Исследует предоставленные материалы, проектирует решения, работает с кодом, исправляет дефекты, проводит тестирование и документирует результаты.

Основная задача: непосредственная инженерная реализация.

3. Critic — независимый проверяющий

Проводит независимый анализ требований, архитектуры, кода, безопасности и результатов. Выявляет дефекты, противоречия и риски, не подменяя собой исполнителя.

Основная задача: независимая оценка качества и соответствия требованиям.

4. Extractor — аналитик инженерного опыта

Извлекает из рабочих материалов полезные навыки, практический опыт, инсайты, технические решения, ошибки и предложения по улучшению.

Основная задача: превращать реальные результаты работы в кандидаты для накопления знаний.

5. Sorter — проверяющий базы знаний

Проверяет подготовленные записи, их структуру, метаданные, соответствие схеме, возможные дубликаты и предполагаемое размещение.

Основная задача: контролируемая проверка новых знаний перед их включением в базу.

6. Consolidator — аудитор базы знаний

Проводит независимый аудит накопленных знаний, выявляет дублирование, устаревшие сведения, противоречия и проблемы доказательности.

Основная задача: поддерживать целостность и качество базы знаний.

Роли не являются шестью независимыми универсальными агентами, которые автоматически работают одновременно. Это специализированные рабочие профили, применяемые в отдельных контекстах в зависимости от задачи.

Цикл инженерной работы

Типовой процесс может выглядеть следующим образом:

1. Пользователь формулирует задачу и определяет ожидаемый результат.
2. Router анализирует задачу и определяет необходимый маршрут.
3. Worker исследует материалы и выполняет согласованную реализацию.
4. Critic проводит независимую проверку, если она необходима.
5. Результат оценивается по заранее определённым критериям.
6. Extractor при необходимости выделяет из опыта работы кандидаты для базы знаний.
7. Sorter проверяет подготовленные записи.
8. Пользователь принимает решение о включении материалов в базу знаний.
9. Consolidator может провести последующий аудит накопленных материалов.

Не каждая задача требует полного цикла. Для небольших и однозначных запросов допустимо непосредственное использование Worker без предварительного запуска Router.

Методологическая основа

Общая инженерная Методика "v5.3" формирует единый подход к работе специализированных ролей.

Она предназначена для поддержки последовательного инженерного процесса: от анализа задачи и определения ограничений до проектирования, реализации, проверки и фиксации результатов.

В числе принципиальных направлений:

- анализ требований и ограничений;
- архитектурное проектирование;
- выбор стратегии реализации;
- работа с техническими рисками;
- проверка соответствия критериям приёмки;
- контроль изменений;
- управление контекстом;
- сохранение доказательности;
- накопление и повторное использование инженерного опыта.

Методика не заменяет специализацию ролей. Она задаёт общую инженерную основу, применяемую с учётом полномочий и задач каждой роли.

Управление знаниями

Отдельное направление экосистемы — создание структурированной базы инженерных знаний.

Она предназначена для сохранения информации, которая может быть полезна в последующих проектах и задачах:

- Skills — применимые навыки и способы решения задач;
- Experiences — зафиксированный практический опыт;
- Insights — обобщённые наблюдения и выводы;
- Negative Memory — сведения об ошибках и неудачных подходах;
- проектные контексты — сведения, относящиеся к конкретным проектам.

Новые материалы проходят предварительную обработку и проверку. Сам факт извлечения информации не означает её автоматического включения в постоянную базу знаний.

Это позволяет отделять исходные наблюдения от проверенных знаний и сохранять происхождение информации.

Начало работы

Для первого знакомства с системой рекомендуется следующий порядок:

1. Открыть "внутренний README" (./ИИ_ИНЖЕНЕРНАЯ_ЭКОСИСТЕМА_v1.9.2_FINAL/README.md).
2. Прочитать "START HERE" (./ИИ_ИНЖЕНЕРНАЯ_ЭКОСИСТЕМА_v1.9.2_FINAL/START_HERE.md).
3. Изучить "каталог ролевых промптов" (./ИИ_ИНЖЕНЕРНАЯ_ЭКОСИСТЕМА_v1.9.2_FINAL/02_ПРОМПТЫ/README.md).
4. Выбрать роль в соответствии с задачей.
5. Передать ей полный файл активного промпта и необходимые исходные материалы.
6. Попросить подтвердить фактически полученные и прочитанные материалы.

Для начала работы не обязательно загружать все компоненты одновременно. Рекомендуется подключать дополнительные документы и базу знаний по мере необходимости.

Важно: отдельные чаты не имеют общей памяти и автоматической связи. Передача контекста между ними в текущей редакции выполняется пользователем вручную с использованием предусмотренных протоколов.

Текущая редакция

Комплект: "v1.9.2"
Методика: "v5.3"
Схема базы знаний: "v1.2"
Контракт ручной передачи: "v2.0.2"

Статус: "CANDIDATE_FOR_VALIDATION"

Редакция включает шесть специализированных ролевых промптов, общую Методику, файловую базу знаний, проектную структуру, протоколы и пользовательскую документацию.

Статические проверки структуры, ссылок, версий и форматов не следует считать подтверждением поведенческой совместимости ролей.

Поведенческие испытания шести ролей и реальные межчатовые передачи на целевых моделях в рамках этой редакции не заявляются как завершённые. Перед эксплуатационным применением необходима отдельная проверка.

До её завершения и соответствующего решения владельца статус "READY_FOR_OPERATION" не присваивается.

Подробности изменений приведены в "Release Notes v1.9.2" (./ИИ_ИНЖЕНЕРНАЯ_ЭКОСИСТЕМА_v1.9.2_FINAL/RELEASE_NOTES_v1.9.2.md).

Ограничения текущей реализации

Для корректной оценки проекта важно учитывать существующие границы:

- автоматическая оркестрация ролей не реализована;
- общая память между отдельными чатами не реализована;
- автоматическая передача файлов и контекста между чатами не предполагается;
- база знаний организована на основе файлов Markdown и YAML;
- фактическая совместимость ролевых промптов зависит от используемых моделей и среды;
- поведенческая проверка требует отдельных испытаний на целевых моделях.

Эти ограничения являются характеристиками текущей редакции, а не основанием приписывать системе неподтверждённые возможности.

Развитие проекта

Дальнейшее развитие экосистемы предполагает последовательную проверку и совершенствование её компонентов.

Ключевые направления:

- поведенческие испытания каждой из шести ролей;
- проверка корректности передачи контекста между ролями;
- проверка соблюдения границ полномочий;
- тестирование обработки неполных и противоречивых входных данных;
- проверка жизненного цикла базы знаний;
- выявление несогласованностей между Методикой, промптами и протоколами;
- улучшение документации на основании результатов реального использования.

Изменения должны опираться на проверяемые результаты, а не только на теоретические предположения.

Участие в развитии

Проект открыт для содержательной обратной связи, предложений по улучшению и технического анализа.

Полезны:

- замечания по архитектуре;
- предложения по улучшению методологии;
- выявленные противоречия и дефекты;
- результаты независимых проверок;
- предложения по повышению воспроизводимости и надёжности;
- конструктивные рекомендации по организации инженерной работы с ИИ.

Перед внесением изменений в глобальные компоненты необходимо учитывать действующие правила и границы полномочий системы.
